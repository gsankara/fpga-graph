# Design C-BRAM (`rand1k`, N=1000) — verified on FABRIC silicon

Date: 2026-10-26. Card: GATECH `probe-gatech` (host `gatech-w3`), Alveo U280,
shell `xilinx_u280_gen3x16_xdma_base_1`, XRT 2.16.204.

The first 1000-vertex graph engine in this repo to run on hardware. Generated by
`graphgen/gen_hls_bram.py`: `GW_N=1000`, `GW_NW=2` host-facing AXI words,
`GW_NW64=16` internal 64-bit lanes, `GW_STAGES=4`, `GW_PAR=8`, `GW_LATCH=1`.

Note for anyone invoking the host: `nw` is **2**, the AXI word count — not 16,
which is the internal lane count. `batch_query graph_engine.xclbin 1000 2 4`.

**Timing closed with the most margin of the three design-C bitstreams:**

| build | WNS | WHS | setup endpoints |
|---|---|---|---|
| `C_tree` | 0.000 ns | +0.006 ns | 0 failing / 448,478 |
| `C_ring16` | +0.007 ns | +0.006 ns | 0 failing / 448,511 |
| **`CB3_rand1k`** | **+0.015 ns** | **+0.006 ns** | **0 failing / 472,295** |

This contradicted the prediction made before the link. HLS estimated 2.433 ns
against an effective budget of 3.33 − 0.90 = 2.43 ns, i.e. 3 ps over before
place-and-route, and the two earlier designs had closed at 0.000 and +0.007 ns.
The inference was wrong: HLS's 0.90 ns uncertainty is a deliberately
conservative routing allowance, and the router beat it on the *densest* of the
three designs. Treat the HLS estimate as a conservative bound, not a forecast.

## Verification

```
rand1k  2709 queries (batched), 0 mismatches -> PASS     (3.07 s)
```

Sampled subsets (empty, 100 singletons, 150 pairs, 50 random of size 3..n) x
9 step counts, via `sim/compare_batch.py` against `graphgen/reference.py`,
driven by `host/batch_query.cpp`. Comparator unmodified from the csim run.

Expansion from a single seed is textbook small-world for degree ~6 with a ring
backbone, and confirms eccentricity 4:

```
k=0 → 1      k=1 → 16     k=2 → 203     k=3 → 951     k=4 → 1000
```

**Negative control.** Pulse-mode reference (`sim_steps(..., 0)`) gives
748 / 2709 mismatches, each differing by exactly the seed vertex. The harness
discriminates.

## Latency — and why this design is different

Median of 4, `k=4`.

| nq | H2D | exec | D2H |
|---|---|---|---|
| 10 | 0.049 ms | 0.109 ms | 0.028 ms |
| 10,000 | 0.135 ms | **30.260 ms** | 0.150 ms |

Marginal cost (30.260 − 0.109) / 9990 ≈ **3.02 µs/query**, about 906 cycles at
300 MHz. HLS predicted 1033 cycles / 3.44 µs, so hardware beat the estimate
again, by ~12%.

Against the small graphs this is a different regime entirely:

| design | N | µs/query | what dominates |
|---|---|---|---|
| `C_tree` | 11 | 0.0103 | fixed ~62 µs call overhead |
| `C_ring16` | 16 | 0.0115 | fixed ~84 µs call overhead |
| **`CB3_rand1k`** | **1000** | **3.02** | **FPGA execution** |

This is the architectural trade of BRAM adjacency, and it is the point of the
design. Baking adjacency into logic gives II=1 — one query per clock — but at
N=1000 it produced 3,359,792 instructions and would not synthesise. Moving the
adjacency into BRAM evaluates `GW_PAR=8` vertices per clock, so a query costs
roughly `GW_N / GW_PAR × GW_STAGES = 500` cycles plus overhead rather than 1.
Synthesisable at N=1000, and no longer one query per clock.

For TODO #1 this inverts the earlier conclusion drawn from the toy graphs: with
a large graph, **PCIe transfer and call overhead are no longer the bottleneck**.
H2D + D2H together are 0.285 ms against 30.26 ms of kernel execution — under 1%.
The fixed ~60-80 µs per-call cost is also negligible here. Latency work on this
design belongs in the kernel, not the transfer path.

`GW_PAR` is the lever: CB4 at `par=16` reported the same 2.433 ns clock for 19%
fewer cycles, at 48% more LUT and 81% more BRAM. It was never linked.

## Caveats

- One card, one site, one session; wall-clock around XRT calls, not counters.
- `load_xclbin` was ~37 ms here because the card already held this bitstream;
  a cold load is ~6.5 s.
